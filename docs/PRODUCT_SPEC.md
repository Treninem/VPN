# AMRI VPN — единое техническое задание

## 1. Назначение

Создать современные Windows- и Android-приложения VPN, которое автоматически выбирает лучший маршрут для каждого сайта, приложения и типа трафика. Пользователь не обязан вручную выбирать сервер.

## 2. Локальный интеллект

Интеллект принятия сетевых решений должен быть собственным и локальным.

Запрещено делать принятие маршрутизационных решений зависимым от внешних AI API, OpenAI, Ollama, облачных LLM или стороннего аналитического сервиса.

Допускается использование обычных программных библиотек и сетевых ядер как технических компонентов транспорта, но решение `какой маршрут использовать` принимает AMRI.

AMRI должен учитывать:

- latency;
- jitter;
- packet loss;
- DNS response time;
- TCP connect time;
- TLS handshake time;
- download/upload throughput;
- историческую успешность;
- стабильность;
- недавние ошибки;
- класс трафика;
- конкретное назначение;
- текущий профиль сети;
- время/исторический профиль нагрузки;
- confidence решения.

## 3. Несколько подписок

Пользователь может добавить несколько VPN-подписок одновременно.

Требования:

- отсутствие искусственного ограничения количества подписок;
- автоматическое обновление каждой подписки;
- единый пул всех узлов;
- дедупликация одинаковых узлов;
- источник узла сохраняется для диагностики;
- приоритет подписки: Preferred / Normal / Backup;
- возможность отключить подписку без удаления;
- статистика рабочих/нерабочих узлов;
- выбор узла независимо от того, из какой подписки он получен.

## 4. Поддерживаемые типы узлов

Архитектура должна предусматривать адаптеры для:

- VLESS;
- VMess;
- Trojan;
- Shadowsocks;
- WireGuard;
- Hysteria2;
- TUIC;
- SOCKS;
- HTTP proxy;
- новых протоколов через расширяемые адаптеры.

## 5. Маршрутизация

Приложение должно поддерживать одновременно несколько выходных маршрутов.

Примеры:

- YouTube → NL-07;
- Discord → DE-03;
- Telegram → FI-02;
- Steam → DIRECT;
- выбранное приложение → VPN ONLY;
- выбранный домен → BLOCK.

Правила могут зависеть от:

- домена;
- IP/CIDR;
- приложения/процесса;
- TCP/UDP;
- порта;
- класса трафика;
- пользовательского правила.

## 6. AMRI RouteScore

У каждого кандидата рассчитывается RouteScore 0–100.

Вес метрик меняется в зависимости от класса трафика.

Для realtime/gaming выше вес latency, jitter и packet loss.

Для video/download выше вес throughput и стабильности.

Для web выше вес DNS/TCP/TLS и общей успешности.

Нельзя выбирать сервер только по минимальному ping.

## 7. Локальное обучение

Локальная БД хранит историю:

`node × destination × network profile × traffic class × time`.

AMRI должен улучшать выбор на основе накопленных измерений.

Пользователь может:

- отключить обучение;
- сбросить обучение для сайта;
- сбросить обучение для сервера;
- сбросить профиль сети;
- полностью очистить историю.

История посещённых назначений не должна отправляться разработчику или третьим лицам без отдельного явного согласия пользователя.

## 8. Проверка серверов

При большом количестве узлов использовать многоступенчатый отбор:

`все узлы → доступные → быстрый probe → расширенный probe → hot pool`.

Нельзя непрерывно выполнять тяжёлый speed test для сотен серверов.

Фоновое исследование альтернатив должно быть ограничено по нагрузке и трафику.

## 9. Failover и устойчивость

Реализовать:

- автоматический failover;
- резервные маршруты;
- quarantine/circuit breaker;
- cooldown;
- hysteresis;
- минимальное улучшение для переключения;
- hot pool готовых маршрутов;
- confidence threshold;
- дополнительное тестирование при низком confidence.

Изменение одного маршрута не должно требовать полного отключения остальных независимых маршрутов.

## 10. Kill Switch

Три уровня:

- Global Kill Switch;
- Application Kill Switch;
- Destination/Rule Kill Switch.

Пример: torrent-клиент при потере VPN блокируется, а браузер может использовать резервный маршрут согласно политике пользователя.

## 11. DNS

Предусмотреть:

- системный DNS;
- DNS через туннель;
- DoH;
- DoT;
- DoQ;
- split DNS;
- DNS cache;
- правила DNS по доменам;
- защиту от утечки DNS.

## 12. Объяснимость

Для каждого решения должен быть экран `Почему?`.

Он показывает:

- выбранный узел;
- RouteScore;
- Confidence;
- важные метрики;
- ближайшие альтернативы;
- причину смены маршрута;
- состояние узла.

AMRI не должен быть чёрным ящиком.

## 13. Интерфейс

Интерфейс современный, с единым design system.

Обязательны:

- скруглённые края;
- карточки;
- современные кнопки;
- pill/toggle-переключатели;
- плавные состояния;
- светлая и тёмная темы;
- простой главный экран;
- отдельный экспертный режим;
- минимум технического шума для обычного пользователя.

Подробности: `docs/UI_DESIGN.md`.

## 14. Архитектура

Основные компоненты:

- `amri-core` — локальное принятие решений;
- `amri-storage` — локальная память;
- `amri-subscriptions` — импорт и объединение подписок;
- `amri-probe` — измерения;
- `amri-federation` — безопасный обмен обезличенным коллективным опытом;
- `amri-transport` — общий реестр и жизненный цикл нескольких транспортных сессий;
- transport adapters — VPN-протоколы/сетевое ядро;
- routing layer — TUN/WFP/DNS/политики;
- Windows UI — управление и объяснение решений;
- Android UI + VpnService — системный lifecycle и packet interface поверх общего Rust-ядра.

Ядро AMRI не должно зависеть от конкретного VPN-протокола.

## 16. Коллективное федеративное обучение

Копии AMRI на разных ПК должны уметь передавать друг другу полезное обучение через собственный AMRI backend, но не личную историю пользователя.

Принцип: `передаём выводы модели, а не события пользователя`.

Разрешается передавать только агрегированные данные: класс трафика, грубый регион выхода VPN, семейство протокола, округлённые показатели качества, стабильность, успешность и небольшие ограниченные изменения весов RouteScore.

Запрещается передавать полный URL, произвольные домены пользователя, историю посещений, IP/MAC пользователя, SSID, имя ПК, Windows SID, постоянный device ID, имена процессов, subscription URL, VPN-ключи/UUID/пароли, cookies/tokens, содержимое трафика и точную геолокацию пользователя.

Обмен коллективным опытом:

- выключен по умолчанию;
- включается отдельным toggle пользователем;
- отправляет только агрегаты после минимального количества локальных измерений;
- имеет лимит размера и частоты batch-пакетов;
- не позволяет одному клиенту сильно изменить общую модель;
- получает подписанную общую модель;
- всегда ставит свежие локальные измерения выше коллективного опыта.

Подробная privacy-модель описана в `docs/FEDERATED_LEARNING.md`.


## AMRI Route Proof

Каждое автоматическое решение может сопровождаться локальной проверяемой квитанцией: версия алгоритма, нормализованные score-компоненты кандидатов, выбранный node, confidence, причина и связь с предыдущей квитанцией. Домен и process name заменяются HMAC-псевдонимом с секретом конкретной установки.

Квитанции позволяют:

- доказуемо обнаружить изменение или удаление записи истории;
- воспроизвести решение офлайн с другим scoring profile;
- построить честный экран «Почему?» без внешней аналитики;
- сбрасывать цепочку вместе с историей обучения по команде пользователя.

Ключ Route Proof никогда не участвует в federated learning и должен храниться в системном защищённом хранилище.
