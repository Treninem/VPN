# AMRI route resilience: hot pool and micro-race

## Цель

Failover не должен ждать последовательный timeout нескольких серверов. Одновременно AMRI не должна постоянно сканировать все узлы из всех подписок: это создаёт лишнюю нагрузку, трафик и фоновые соединения.

Поэтому быстрый failover разделён на два уровня:

1. `amri-core::build_hot_pool` заранее поддерживает маленький качественный набор резервов.
2. `amri-probe::race_tcp_hot_pool` выполняет короткую параллельную проверку только этого набора непосредственно перед переключением.

## Hot pool

По умолчанию сохраняется до 4 кандидатов.

Кандидат должен:

- не быть statically quarantined;
- не находиться в активном cooldown `RouteHealthTracker`;
- пройти минимальный RouteScore;
- пройти минимальный confidence;
- не отставать от лучшего кандидата сильнее заданного relative score floor.

Первые reserve slots предпочитают разные `provider_id`. Это уменьшает риск, что основной маршрут и все резервы одновременно исчезнут при проблеме одного провайдера/подписки. После набора требуемого provider diversity оставшиеся места заполняются строго по RouteScore.

Provider diversity никогда не должна протаскивать явно плохой маршрут: relative score floor применяется раньше разнообразия.

## Micro-race

`race_tcp_hot_pool` запускает не больше `max_parallel` коротких TCP probes. Значения по умолчанию намеренно агрессивные, потому что race применяется к уже отобранным hot candidates, а не к неизвестным узлам:

- per-target timeout: 650 ms;
- общий caller-visible budget: 750 ms;
- settle window после первого успешного ответа: 35 ms;
- максимум параллельных кандидатов: 4.

После первого успешного ответа AMRI не ждёт окончания всех timeout. Она даёт только небольшое settle window, чтобы почти одновременно ответивший, но существенно более быстрый кандидат мог выиграть.

Если первый кандидат неуспешен, race продолжается до первого успеха или общего deadline.

## Почему не выбирается просто первый ответ

Первый завершившийся TCP connect может выиграть из-за scheduler jitter на несколько миллисекунд. Поэтому после первого успеха оставляется маленькое settle window, а победитель среди полученных успешных результатов выбирается по измеренному TCP/latency quality. Это даёт быстрый ответ без жёсткой зависимости от порядка выполнения потоков.

## Ограничение нагрузки

Race не принимает сотни серверов как рабочий сценарий. Вызов намеренно обрезает список до `max_parallel`; больший unified subscription pool сначала должен пройти обычный scoring/hot-pool отбор.

Параллельные probe-потоки не блокируют возврат результата после deadline/settle window. Количество таких потоков жёстко ограничено размером hot pool.

## Приватность

Hot-pool race проверяет только endpoint VPN-узла (`host:port`). В этот механизм не передаются посещаемые домены, URL, процессы пользователя, история браузера, идентификатор устройства или содержимое трафика.

## Следующая интеграция

После выбора winner orchestration layer должен:

1. записать success/failure probes в `RouteHealthTracker`;
2. повторно применить `select_stable`/hysteresis;
3. при реальной смене выхода вызвать `TransportManager::replace`;
4. переключить packet-routing layer только после успешного make-before-break transport handoff.

Такой порядок сохраняет разделение ответственности: probe измеряет, AMRI core принимает решение, transport запускает соединение, routing layer переключает пакеты.
